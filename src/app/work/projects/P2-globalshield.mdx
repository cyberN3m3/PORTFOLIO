## Overview

A multi-region disaster recovery setup on AWS with automatic failover from us-east-1 to us-west-2. The site is served from S3 buckets in both regions behind one CloudFront distribution; if the primary origin returns errors, CloudFront retries the request against the secondary without anyone touching DNS. Running costs stay within the AWS Free Tier.

## What it does
- **Automatic failover**: a CloudFront origin group sends requests to the backup region when the primary returns errors. Nobody has to change DNS.
- **Two regions**: the same site is hosted on S3 in us-east-1 and us-west-2.
- **Status dashboard**: a dark-mode page with simulated incident and recovery modes that shows which region is serving and whether failover has happened.
- **All in Terraform**: both regions and CloudFront are deployed with Terraform, using provider aliases for the second region.
- **Health Monitoring**: a Route 53 health check watches the primary endpoint, so an outage is visible even while CloudFront is already serving the backup.

## Technologies Used

- **AWS CloudFront**: the single entry point, with HTTPS and the origin group that handles failover.
- **Amazon S3**: static website hosting in both regions, each with its own dashboard.
- **AWS Route 53**: health check on the primary endpoint.
- **Terraform**: the whole setup as code.
- **HTML and Tailwind CSS**: the dashboard, set in JetBrains Mono and Inter.

## Challenges and Learnings

The key challenge was getting real failover without paying for idle servers in a second region. CloudFront origin groups solved it: failover happens per request at the edge, and the standby region is just an S3 bucket that costs almost nothing until it is needed. The other challenge was the dashboard: it had to make clear, at a glance, which region was serving and whether failover had happened, without burying people in technical detail.

## Outcome

The project shows an active-passive disaster recovery pattern working end to end at almost no cost, and taught me multi-region Terraform (provider aliases), CloudFront origin groups and failover criteria, and how to show system state clearly on a dashboard. The same pattern is a sensible first step for any static site or front end that must survive a regional outage.
